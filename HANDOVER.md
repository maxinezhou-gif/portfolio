## 4 · Interactions — agreed, with exact values

Three interactions were prototyped, measured and chosen. Each has a lab file
if it needs retuning.

### 4.1 Sticky label swap — `("scrolly", …)` · SHIPPED

Left label column pins; as each image reaches the pin line its label replaces
the previous one.

| | |
|---|---|
| Chosen | **fade + rise, 600ms** (variant B in the lab) |
| Tokens | `--swap-dur: 600ms` · `--swap-rise: 6px` · `--swap-ease: cubic-bezier(.2,.7,.3,1)` |
| Pin | `top: 80px` (clears the 55px top bar) |
| Collapses | below 1040px |
| Lab | `_prototype/sticky-lab.html` — six variants, live drift readout |

**Two rules this depends on. Break either and it visibly jumps:**

1. **Keep the section intro OUT of the scrolly.** Put it in a `head` block
   above. Originally the first label block also carried the intro, so its
   heading sat ~180px lower than the others and the swap leapt.
2. **Give every label the same shape** — `h3` + one `small`, or `h3` +
   `questions`. Verified: heading offset **0px** in every block, so the label
   changes in place.

Exactly one label is ever visible — JS marks the active one and hides the rest.
An opaque backdrop was tried first and **was not sufficient**: the blocks pin
and unpin at different moments, so a transiting block left the previous one
exposed. Don't go back to that.

### 4.2 Before/after reveal — `("reveal", …)` · JUST ADDED, NEEDS A LOOK

Two full-viewport frames; the AFTER crossfades in over the BEFORE as you
scroll, and uncovers on the way back.

| | |
|---|---|
| Chosen | **fade variant at 100vh** |
| Mechanism | both panes `position: sticky; top: 0`, after has higher z-index |
| Driver | `--reveal-p` (0→1) set per section in `case-study.js` |
| Lab | `_prototype/reveal-lab.html` — cover / card / wipe / fade |

**Verification status — read this.** Re-measured in the second session, more
thoroughly. Everything static now checks out:

| Checked | Result |
|---|---|
| Section height | **exactly 2 × viewport** (1534 at vh 767) |
| Pane geometry over 11 scroll positions | `afterTop` 767→0 **linear**, `beforeTop` pinned at 0 |
| `--reveal-p` → opacity binding | **1:1** at 0 / .25 / .5 / .75 / 1 |
| `transition-duration` on the after pane | `0s` — opacity tracks scroll with no lag |
| Full-bleed | section width == document width |
| Tags, images | both present; 2000×1250, loaded |

**The fade itself still cannot be seen here**, and the reason is now precisely
understood: `requestAnimationFrame` **never fires** when the Browser pane is
hidden, so the driver's `paint()` never runs and `--reveal-p` freezes at a
stale value. That is an environment artefact, not a page bug — see §7.
Screenshots come back blank, and no real Chrome was connected.

**One finding that changes what to look for.** Hit-testing at the midpoint
shows the AFTER pane covers only the **bottom half** of the viewport — its top
edge sits at y=383 of 767, at 50% opacity, with pure BEFORE above it. So this
is **rise + fade with a travelling horizontal seam**, not a full-viewport
crossfade. That is inherent to `sticky` + opacity and the lab's fade variant
does the same, so it is presumably what was chosen — but the wording above
("crossfades in over") implies something it does not do. **When you look at
it, the question is whether that seam reads as intentional.**

**Aspect ratio matters here.** The frames are 1.6:1, so at **1440×900 there is
zero crop**, but at 1440×800 the bottom 11% is lost. Keep nothing critical in
the bottom band of any replacement frame.

**Still needs a real browser:** open `work/design-system-migration.html`,
scroll the reveal down and back up, then resize under 1040px and confirm you
get two plain stacked images.

Currently using `ds-before.jpg` / `ds-after.jpg`. Maxine has made **two

### 4.3 Homepage row hover — BUILT, ONE PROBLEM OPEN

Reference: **niklas.space**, analysed in §5. Built in the second session as a
**travelling dot + hover preview** in Maxine's tokens.

| | |
|---|---|
| Dot | 16px, `--accent`, **−24px x / +15px y** from the row; at rest beside the top-bar name |
| Preview | 560×350 media + 4px white frame, `--r-sm`, two-layer grey shadow |
| Anchor | **+296px from the row's LEFT edge** (the measured reference offset), vertically centred on the row, then clamped to the viewport |
| Motion | `--dot-dur: 420ms` with `--swap-ease`. Deliberately **not** `--swap-dur` (600ms) — that is a scroll transition; this tracks a pointer |
| Off below | 1040px, and on any `(hover: none)` device |
| Media cost | `preload="none"`, empty `src` until first hover — **a visitor who never hovers downloads no preview media at all** |

Both are single elements that MOVE rather than appear, which is what makes it
read as one indicator and one preview rather than seven of each.

**Two bugs were found and fixed here; do not reintroduce them.**

1. The dot's reveal was gated on a `requestAnimationFrame` callback. A page
   loaded in a **background tab** never gets that callback, so the dot stayed
   at `opacity: 0` permanently — still invisible when you returned to the tab,
   with nothing left to retrigger it. It is now synchronous (suppress the
   transition, place, force a reflow, restore, reveal). **Nothing here may
   depend on a frame ever being painted.**
2. Moving between rows fired `mouseleave` on the old row **before**
   `mouseenter` on the new one, so the preview faded out and back in on every
   row change — a flicker down the whole list. Leaving is now deferred 60ms
   and cancelled if another row claims the preview.

## 7 · Verification — what this environment can and cannot prove

Hard-won. Do not waste time rediscovering it.

**Works reliably:** computed styles, geometry, `elementFromPoint`, layout
measurement at any viewport (via an offscreen iframe), link/asset integrity,
alt-text checks.

**Does not work when the Browser pane is hidden** (it reports
`document.hidden: true`, so the page never composites):

- **`requestAnimationFrame` NEVER fires.** This is the big one, confirmed in
  the second session with a direct probe (0 callbacks in 600ms). Any rAF-gated
  code looks completely dead: `--reveal-p` froze at one stale value across all
  eleven scroll positions for exactly this reason, and the homepage dot never
  got its `is-ready` class. **Before concluding a scroll driver is broken,
  check whether it goes through rAF.** It almost certainly does — that is the
  correct way to write one.
- **Scroll events are unreliable, not absent.** 24 fired early in the second
  session, then they stopped. Do not rely on either behaviour.
- `setInterval` is throttled to roughly one tick per 600ms
- **IntersectionObserver never fires** — not even its initial callback
- **CSS transitions do not run**, so timing measurements are meaningless
- **Screenshots come back blank** — confirmed again
- Late in a session, even `scrollTo` stops moving the page

**Claude in Chrome is not a way around this.** `list_connected_browsers`
returned `[]` — there is no real browser to drive. Checked, so you do not have
to.

**The trap that wasted the most time in the second session:** because
transitions never advance, **`getBoundingClientRect()` returns the value the
element started at, not the one JS just set.** The homepage dot read as stuck
at `-100,-100` while the JS was in fact computing correct positions every time.

> **Measure `el.style.translate` (the specified value), not the rect**, when
> you are verifying JS-driven positioning. The rect is lying to you.

Two more mechanical gotchas:

- **`html { scroll-behavior: smooth }` is set site-wide**, so `scrollTo` lands
  short and your measurement steps silently drift. Set it to `auto` before any
  stepped scroll measurement.
- Measuring at several viewports is best done with an **offscreen iframe**;
  remember to cache-bust the **stylesheet** inside it too, not just the page.

So: **anything scroll-driven, animated, or video-related cannot be confirmed
here.** Verify structure and geometry by measurement, then ask Maxine to check
motion in a real browser. Say plainly which is which — she is fine with the
limitation, but not with it being glossed over.

**Two traps that produced wrong conclusions in this session:**

- **Stylesheet caching.** After editing CSS, the browser served the old file
  and the new component appeared to do nothing. Cache-bust the *CSS*, not just
  the HTML.
- **Unrevealed `.rv` elements.** They carry `translateY(14px)`, which silently
  poisons any spacing measurement. Add `.in` and let the transition finish
  (~700ms) before measuring.
